# Общая оплата и СБП для одного платежа

В версии 1.2.0 подготовлен альтернативный сценарий с
embedded-виджетом ЮKassa. Он выключен по умолчанию. Включение требует отдельной
проверки магазина и решения владельца; серверные настройки не менялись.

## Что меняется при включении

API создаёт один платёж с `confirmation.type=embedded` и `capture=true`.
`confirmation_url` ведёт на нашу страницу `/checkout`, `sbp_confirmation_url`
— на ту же страницу с `mode=sbp`. Сумма, `payment.id`, результат и
`confirmation_token` общие. Переключение режима меняет только конфигурацию
виджета: все доступные способы либо `payment_methods=['sbp']`.

Это замена общей внешней redirect-ссылки для новых платежей при включённом
флаге. Две внешние ссылки ЮKassa для одного redirect-платежа не заявляются
поддержанными. При выключенном флаге новые платежи используют прежний redirect;
старые платежи не конвертируются и не создаются повторно.

В списке незавершённых платежей показывается дополнительная кнопка СБП для
новых widget-платежей. На странице оплаты есть оба режима и проверка статуса.
В 1.2.1 выбор оформлен двумя карточками: «Картой и другими способами» и «СБП».
Первая открывает общую форму ЮKassa с доступными магазину способами; название
не ограничивает оплату клиентами Сбера. Вторая сразу выбирает режим СБП.
Такие же карточки доступны у незавершённого widget-платежа.
Переход к оплате, переключение, reload, новая вкладка и возврат из банка не
вызывают создание нового платежа. За начисление и выдачу подписки отвечают
прежние серверные webhook и сверка с провайдером, с их идемпотентностью.
Сообщение виджета само по себе ничего не начисляет.

## Доступ к странице

Ссылка содержит подписанный ticket, ограниченный одним платежом и владельцем,
на один час. Он подписан производным ключом отдельного назначения и не может
использоваться как JWT кабинета. Это bearer-ссылка: получивший её сможет
оплатить этот конкретный платёж и увидеть его сумму и статус, но не профиль,
баланс, другие платежи или способы входа клиента. Не публиковать её.

Ticket находится во фрагменте URL, не передаётся серверу frontend в запросе
страницы и удаляется до загрузки скрипта виджета. Для reload сохраняется только
в `sessionStorage` этой вкладки. В URL возврата банка сохраняется та же
ограниченная ссылка, чтобы восстановить оплату и при смене контекста браузера.
Отдельная ссылка позволяет открыть оплату из
Telegram во внешнем браузере без переноса пользовательской сессии кабинета.

`POST /api/v1/payments/yookassa/checkout` принимает ticket в JSON и возвращает
только данные оплаты. Ответ имеет `Cache-Control: no-store`. Backend проверяет
подпись, назначение, срок, владельца, состояние аккаунта и платежа. После
успеха, отмены или истечения срока токен формы не выдаётся. Проверка страницы
не создаёт и не изменяет платёж. После истечения ticket нужна новая оплата
из кабинета; истёкший часовой widget-платёж не переиспользуется.

В 1.2.1 исправлено ошибочное включение этого endpoint в группу авторизации
кабинета. Только чтение checkout доступно без пользовательской сессии, по
платёжному ticket; остальные payment endpoints остаются защищёнными.
Регрессионные API-тесты проверяют это без подмены `get_current_account`.

`confirmation_token` сохраняется в существующем JSON metadata платежа, чтобы
не потеряться после ответа webhook/сверки, где он может уже отсутствовать.
Миграция БД не требуется. Полные ссылки, ticket, confirmation_token и банковские
данные не должны попадать в журналы API/proxy/аналитики. Данные карты вводятся
в форме ЮKassa, приложение их не собирает.

## Настройки для будущего включения

1. Уточнить у менеджера ЮKassa разрешение на настройку способов оплаты
   `customization.payment_methods` и поддержку СБП у конкретного магазина.
   При отсутствии разрешения виджет возвращает
   `customization_of_payment_methods_not_allowed`; пользователь может выбрать
   общую форму того же платежа.
2. Подготовить тестовый магазин и frontend с маршрутом `/checkout`.
   `WEBAPP_URL` должен указывать на frontend, не на бота. Reverse proxy должен
   отдавать SPA для `/checkout`. Проверить HTTPS и разрешения iframe/скрипта
   `https://yookassa.ru/checkout-widget/v1/checkout-widget.js` в CSP, если она
   задаётся внешним proxy.
3. На отдельном тестовом API установить `YOOKASSA_WIDGET_ENABLED=true`.
   API читает этот флаг через существующий `env_file` Compose; дополнительный
   frontend-флаг не нужен. В обоих примерах `.env` значение по умолчанию false.
4. Проверить одну сумму и один `payment.id` в двух ссылках, отмену, истечение,
   две вкладки, повтор webhook и сверку. В тестовом магазине возможности СБП
   могут отличаться: успешный тест картой не подтверждает реальное СБП.
5. После согласования сценария и проверки разрешений — отдельная команда
   владельца на production-деплой/включение. До этого флаг оставить false.

Остаётся проверить настоящий QR на desktop, выбор банка на телефоне и возврат
из банка/Telegram, включая браузеры с ограничениями storage и всплывающих окон.
Автоматические тесты используют подменённый SDK/скрипт виджета; доступность
СБП в магазине и списки банков ими не подтверждаются.
