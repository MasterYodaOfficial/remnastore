## Схема

Кнопка вызывает `supabase.auth.signInWithOAuth({provider: 'custom:yandex'})`.
Supabase управляет state, PKCE и обменом кода Яндекса на токен. Затем вызывает
`GET /api/v1/auth/yandex/userinfo` нашего API с токеном Яндекса в Authorization.
API обращается только к `https://login.yandex.ru/info?format=json`, проверяет
`client_id` и преобразует `id` в `sub`, `default_email` в `email`, имена —
в стандартные claims. Токены и полный профиль не сохраняются и не логируются.
Адаптер не выдаёт сессии: обычную сессию выдаёт Supabase.

Backend сопоставляет `custom:yandex` с существующим `AuthProvider.YANDEX`.
Повторный вход разрешается по Supabase ID / внешней identity, сохраняя
связанный Telegram-аккаунт. Уже существующая логика поиска локального аккаунта
по подтверждённому email не изменялась.

Яндекс `/info` не возвращает `email_verified`. В локальной ветке
`fix/auth-recovery-email` адаптер передаёт `true` только для валидного адреса,
локальная часть которого совпадает с серверным `login`, в доменах `yandex.ru`,
`ya.ru`, `yandex.com`, `yandex.by`, `yandex.kz`. Это правило доверия проекта,
а не признак из ответа провайдера. Остальные контакты получают `false`:
Supabase может запросить подтверждение и вернуть `provider_email_needs_verification`.
Глобальное автоподтверждение не включается. Основания, ограничения и план
проверки: [исправления browser auth](auth-recovery-email.md).
Проверки ниже относятся к исходной интеграции; новые исправления пока не
проверялись, общий прогон отложен по просьбе владельца.

## Настройки для будущего развёртывания

1. В приложении Яндекс выбрать веб-сервис, разрешения `login:email`, `login:info`.
   Зарегистрированный Redirect URI:
   `https://auth.myquickcloud.online/auth/v1/callback`.
2. В окружении API установить `YANDEX_OAUTH_CLIENT_ID` равным Client ID.
   Без значения адаптер возвращает 503; с токеном другого приложения — 401.
3. В окружении Supabase Auth установить
   `GOTRUE_CUSTOM_OAUTH_EXTERNAL_URL=https://auth.myquickcloud.online/auth/v1`.
   В GoTrue v2.197.0 к этому значению автоматически добавляется `/callback`.
   Это настройка custom-провайдеров; существующий Google Redirect URI не менять.
4. Развернуть API с адаптером. Вызов без токена должен вернуть 401 и no-store.
5. Создать провайдер через admin API, используя скрипт ниже. Он читает секрет
   из защищённого серверного JSON (`client_id`, `client_secret`), выводит только
   результат, по умолчанию оставляет провайдер выключенным. Требуется доступ
   к Docker и self-hosted Auth с текущим JWT secret в окружении контейнера.

   ```sh
   python3 scripts/configure_yandex_auth.py \
     --auth-container quickcloud-auth-auth-1 \
     --credentials-file /opt/supabase-auth/yandex-credentials.json \
     --userinfo-url https://configsb.myquickcloud.online/api/v1/auth/yandex/userinfo
   ```

   После проверки конфигурации повторить с `--enable`. Скрипт обновляет
   существующий `custom:yandex`, не создавая дубликаты.
   Client Secret передаётся только в Auth; не добавлять его в VITE-переменные.
   Формат scopes не передаётся: используются разрешения зарегистрированного
   приложения Яндекс, чтобы избежать несовпадения разделителей scopes.
   Начиная с выпуска 1.1.0 инструкция и скрипт включаются во вложения GitHub
   Release. Если скачан отдельный `configure_yandex_auth.py`, запускайте его
   из каталога загрузки без префикса `scripts/`; остальные параметры те же.
6. Развернуть frontend и установить `VITE_YANDEX_AUTH_ENABLED=true` в его
   runtime-окружении. До этого кнопка скрыта. Локальный Vite читает переменные
   из `apps/web/.env`; корневой `.env` автоматически не подхватывается им.

Скрипт рассчитан на существующую конфигурацию хранения секретов Supabase;
в установленной версии без DBEncryption секрет custom-провайдера хранится
в БД открытым текстом. Не выводить его в дампы диагностики и защищать резервные
копии БД так же, как серверные env-файлы.

## Проверка перед включением

- Проверить, что authorize redirect содержит нужные client_id, redirect_uri,
  state и PKCE challenge; scope соответствует разрешениям приложения.
- Первый вход, отказ в разрешении, недоступность Яндекса и истёкший код.
- Вход без письма для доверенного почтового логина, подтверждение остальных
  адресов, переход ранее неподтверждённых пользователей; баланс, подписка и Telegram
  остаются в исходном аккаунте, новые дубликаты не создаются.
- Проверить конфликт существующих identities и аккаунта с тем же email.
- Проверить referral intent, обновление сессии, выход и вход с мобильного.
- Проверить Google, email/password и recovery после настройки custom callback.

Локальные автоматические проверки покрывают адаптер, неправильный client_id,
ошибки upstream, отсутствие email/sub, выключенную конфигурацию, повторный вход
и сохранение Telegram identity, кнопку и сообщения OAuth. Они не заменяют
полный вход через Яндекс и доставку письма на действующей установке.

Дополнительно проверены браузерные сценарии с подменённым endpoint Supabase:
кнопка запускает `custom:yandex` с PKCE, referral intent сохраняется, ошибки
