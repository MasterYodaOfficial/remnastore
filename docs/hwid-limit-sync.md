# Синхронизация лимита HWID

Локальная ветка `feature/hwid-limit-sync` создана 26 октября 2026 года от
актуального `dev` после слияния PR #35. Изменения не развёрнуты на сервере.

## Источник лимита

Лимит перечитывается из Remnawave при открытии или обновлении раздела устройств,
перед расчётом и оплатой дополнительных устройств, при расчёте продления
для аккаунта с сохранёнными настройками устройств. Webhook и ручная сверка
подписки также обновляют существующие настройки устройств.

Webhook использует свежий GET пользователя, а не значение лимита из тела события:
задержавшееся или повторное событие не должно возвращать старое значение.
Если настройки устройств ещё не созданы, они будут инициализированы при первом
открытии раздела или покупке; webhook не создаёт их для всех пользователей.

- Положительное значение `hwidDeviceLimit` — общий лимит пользователя.
- `0` — безлимит. Это не отсутствие настройки и не ноль доступных устройств.
- `null` — наследование настроек панели. API читает `hwidSettings` External Squad,
  если переопределение задано, иначе — `/api/subscription-settings`.
  При выключенном HWID результат — безлимит, при включённом берётся
  `fallbackDeviceLimit`. Не подставляется лимит тарифа RemnaStore.
- Если получить или проверить настройки не удалось, старый лимит сохраняется.
  Ошибка не превращается в безлимит или пустой подтверждённый список устройств.

Наследование и переопределение описаны в
[документации Remnawave](https://docs.rw/features/hwid-device-limit/).
Поля и маршруты сверены с установленным Python SDK Remnawave 2.8.

## Оплаченные дополнительные устройства

В панели хранится общий лимит, в RemnaStore — базовый лимит и оплаченные
дополнительные устройства. Например, при двух оплаченных устройствах ручной
общий лимит `8` означает базовый `6`, а не `8 + 2`.

При сверке не меняются число оплаченных устройств, выбор на следующее продление,
предоплаты, баланс и срок подписки. Меняется только базовый лимит и revision;
прошлый расчёт покупки становится недействительным до списания денег.
Изменение записывается в историю `devices.limit_synced` с источником,
состояниями до/после и общим лимитом панели. Повторная сверка того же значения
не создаёт повторное изменение.

Защитное правило для ручного общего лимита, который не оставляет места
оплаченным устройствам и хотя бы одному базовому: сохранить локальные права
и деньги, показать `conflict` с фактическим лимитом панели и отклонять новые
расчёты/покупки с `devices_limit_conflict`. Панель автоматически не исправляется,
возвратов и удаления оплаченных прав при сверке нет. Это выбранный для локальной
реализации безопасный вариант; бизнес-правило можно изменить отдельно.
Базовый `0` не используется для представления такого конфликта, поскольку
в действующем контракте он означает безлимит.

При ручном включении безлимита уже оплаченные устройства и предоплаты
сохраняются. Следующий расчёт продления по умолчанию не навязывает покупку
новых дополнительных устройств; обычный подтверждаемый перерасчёт остаётся
частью существующего процесса продления.

## Незавершённые оплаты и недоступность панели

Во время применения оплаченной покупки или незавершённого grant лимит
не переинтерпретируется как ручное изменение: удалённая запись могла уже
сработать, а локальное подтверждение — ещё нет. Показывается `pending`,
существующий механизм повторов завершает оплату, затем сверка возобновляется.
Это защищает от двойного учёта дополнительных устройств после потери ответа.

Для уже сохранённых настроек `GET /api/v1/devices` возвращает последний
подтверждённый лимит и `limit_sync_status=unavailable` при ошибке панели.
Если список устройств прочитать не удалось, `devices=null`, а не `[]`.
Клиент показывает предупреждение, сохраняет лимит и предлагает повторную
проверку. Покупки и изменение выбора продления в таком интерфейсе отключены.
Если подтверждённых настроек ещё нет, возвращается обычная ошибка доступности.

Ошибки сверки из webhook/ручной сверки подписки записываются в
`devices.limit_sync_failed`; недостоверное тело webhook не используется
как запасной источник лимита. Удаление пользователя в панели не очищает
оплаченные записи устройств: оно остаётся частью существующего lifecycle подписки.

## Контракт и проверка

Новые поля `GET /api/v1/devices`: `limit_sync_status` (`synced`, `pending`,
`unavailable`, `conflict`) и `panel_limit` (подтверждённый общий лимит панели,
либо `null`, когда он неизвестен). `limit` при конфликте/сбое остаётся локальным
подтверждённым правом; он не выдаётся за текущий лимит панели. Изменённое поле
`devices` допускает `null`. Миграции и новые env-переменные не требуются.

Автоматические проверки охватывают изменения после создания настроек,
webhook со старым значением, пропущенный webhook и сверку при чтении,
разницу `null`/`0`, External Squad, сбой и повтор, сохранение оплаченных
устройств, отбрасывание старого расчёта до списания и незавершённую покупку.

Перед будущим деплоем проверить на тестовой панели: ручное увеличение и
уменьшение общего лимита, переключение в наследование и безлимит,
конфликт с оплаченной квотой, пропуск webhook и недоступность панели.
Раздел устройств должен показывать актуальный результат после «Обновить».

Локально прошли 114 профильных API-тестов (33 — устройства, 17 — клиент
Remnawave, 64 — подписки, покупки и привязка аккаунтов), 63 unit-теста frontend
и все 23 браузерных теста. Проверены Ruff, frontend lint, TypeScript,
production-сборка и описание выпуска 1.1.0. Это не полный прогон API и не
проверка работающей панели; внешние ответы в тестах подменены.
