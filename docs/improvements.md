## 3. Завершить сценарий сброса пароля через Supabase

**Статус:** локальные исправления подготовлены в `fix/auth-recovery-email`;
общий прогон и проверка реального письма отложены до следующих дополнений.
**Добавлено:** 25 октября 2026 года.

Реализация и оставшиеся проверки: [исправления browser auth](auth-recovery-email.md).
Чек-листы ниже считаются окончательно закрытыми после общего прогона,
который по просьбе владельца сейчас не запускался.

### Проблема

По наблюдению владельца сервиса, ссылка из письма создаёт сессию, после чего
открывается обычный личный кабинет. Ожидается форма нового пароля и его
подтверждения. Само создание сессии не означает, что пароль сброшен:
сценарий завершён только после успешного сохранения нового пароля.

### План доработки

- [ ] Определять намерение сброса до восстановления обычного кабинета:
  учитывать `auth_action=reset-password`, подтверждённый режим текущей
  recovery-сессии и событие `PASSWORD_RECOVERY`. Маркер URL управляет экраном,
  но не заменяет проверку действительной сессии для сохранения пароля.
- [ ] Сделать recovery приоритетным состоянием в инициализации, обработке
  `SIGNED_IN` / `INITIAL_SESSION` / `TOKEN_REFRESHED` и отрисовке.
  Защитить отложенные результаты bootstrap-запросов от открытия кабинета
  до успешной смены пароля.
- [ ] Восстанавливать незавершённый recovery после перезагрузки в той же вкладке,
  проверяя актуальность сессии. Сбрасывать маркер при успешном сохранении,
  явной отмене или недействительной сессии.
- [ ] Проверить фактический переход из письма: итоговый URL, сохранение
  `auth_action`, PKCE code exchange, доступность verifier и получение
  `PASSWORD_RECOVERY`. Сверить redirect allowlist и шаблон письма в Supabase.
  Для диагностики фиксировать этапы и названия событий без токенов и паролей.
- [ ] Подключить экран `recovery-expired` для просроченной, повторно
  использованной или некорректной ссылки и ошибок PKCE; дать запросить новое
  письмо. Проверить открытие в другой вкладке, браузере и на другом устройстве,
  включая понятный результат при отсутствии verifier.
- [ ] Разрешать переход в кабинет только после успешного `updateUser`.
  При ошибке сохранять форму с сообщением и возможностью повторить сохранение;
  проверить отмену и завершение recovery без повторного входа по старому состоянию.
- [ ] Добавить unit/component и e2e проверки перечисленных переходов,
  включая гонку bootstrap с `PASSWORD_RECOVERY`, и провести ручную проверку
  с реальным письмом. При реализации обновить `apps/web/FRONTEND_CONTRACT.md`.

### Критерии готовности

- [ ] Действительная ссылка открывает форму нового пароля и подтверждения,
  в том числе при уже существующей browser-сессии; кабинет до сохранения не показывается.
- [ ] Перезагрузка формы в той же вкладке сохраняет режим сброса при действующей сессии.
- [ ] Несовпадающий или слишком короткий пароль не отправляется; ошибка
  сохранения не переводит пользователя в кабинет.
- [ ] После успешного сохранения доступен вход с новым паролем, старый пароль
  больше не подходит; временные recovery-маркеры очищены.
- [ ] Недействительная ссылка и отсутствие PKCE verifier дают понятный экран
  с запросом нового письма, даже если в браузере есть старая сессия.
- [ ] Отмена возвращает к входу, обычный email/OAuth-вход продолжает работать.
- [ ] Автоматические проверки и ручной сценарий «письмо → форма → сохранение
  → вход с новым паролем» пройдены.

Дополнительное подтверждение почты при входе через Яндекс рассматривается

## 5. Полностью переработать админку для сопровождения клиентов

**Статус:** запланировано; требуется переработка интерфейса и расширение admin API.
**Добавлено:** 25 октября 2026 года.

### Цель

Сделать админку понятным рабочим инструментом: быстро найти клиента, понять
причину проблемы, выполнить доступное действие и увидеть результат и историю.
Пересмотреть структуру экранов, навигацию, визуальную иерархию и повседневные
сценарии поддержки. В объём входят необходимые изменения backend, схем БД,
интеграций и фоновых задач, если без них сценарий нельзя завершить из интерфейса.

### Основные проблемы

Логика и разметка сосредоточены в большом `App.tsx`; карточка клиента перегружена,
разделы не имеют самостоятельных адресов. Нужна понятная визуальная иерархия,
плотная компоновка и единые сценарии сопровождения. Не хватает полноценного
реестра платежей, admin API устройств, заметок, обращений и общей модели прав.
Существующие действия нужно сохранить при переработке.

### Новая структура интерфейса

- [ ] Сделать постоянную боковую навигацию по рабочим разделам: «Обзор»,
  «Клиенты», «Обращения», «Платежи и выводы», «Тарифы», «Промокоды»,
  «Рассылки», «События и диагностика», «Администраторы и доступ».
  В шапке разместить глобальный поиск и задачи, требующие внимания.
- [ ] Ввести адреса разделов и отдельных сущностей, breadcrumbs и прямые
  ссылки на клиента, платёж и обращение. Назад/вперёд и перезагрузка должны
  сохранять контекст, фильтры и страницу списка.
- [ ] Перенести подробную карточку клиента на отдельную страницу с краткой
  сводкой и вкладками: обзор, подписка и устройства, финансы, авторизация
  и привязки, обращения и заметки, события. Быстрый просмотр оставить компактным.
- [ ] Собрать единые таблицы, фильтры, статусы, формы и подтверждения действий.
  Настроить типографику, отступы, контраст, плотность данных и читаемые суммы
  и даты с явным часовым поясом; статусы различать текстом и цветом.
- [ ] Убрать декоративный шум, продумать пустые состояния, загрузку, ошибки
  и повтор запроса. Формы открывать по действию, показывать результат рядом
  с изменёнными данными. Проверить клавиатуру, фокус и небольшие экраны.
- [ ] Декомпозировать `App.tsx` на страницы, общие компоненты и слой работы
  с API; загружать историю и тяжёлые разделы по мере открытия.

### Требования к backend и операциям

- [ ] Переиспользовать действующие сервисы ledger, платежей, подписок,
  устройств и уведомлений. Финансовые изменения проводить через ledger,
  а не прямой записью баланса или ручной установкой статуса «оплачен».
- [ ] Добавить admin endpoints для недостающих сценариев с правами на каждое
  действие, валидацией, понятными кодами ошибок и серверной пагинацией/фильтрами.
- [ ] Для денежных операций, выдачи/продления подписки, возвратов и повторов
  обработки предусмотреть идемпотентность и защиту от параллельных действий.
  Перед изменением показывать клиента, последствия и итоговые значения;
  сохранять причину, оператора и результат в аудите.
- [ ] Для операций с внешней системой отображать состояния «выполняется /
  успешно / ошибка» и проверяемый итог. Предусмотреть восстановление после
  частичного сбоя, чтобы интерфейс не сообщал успех раньше фактического результата.
- [ ] При ручном изменении подписки или устройств явно показывать, как оно
  влияет на оплаченный срок, дополнительные устройства и дальнейшее продление.
- [ ] Хранить обращения и заметки в БД, ограничивать их видимость правами;
  добавлять миграции и тесты новых правил вместе с реализацией.

### Порядок реализации

1. **Основа интерфейса:** карта сценариев поддержки, новая навигация, общие
   компоненты, реестр клиентов и полноценная страница клиента. Проверить
   компоновку на реальных объёмах данных и перенести существующие действия.
2. **Базовое сопровождение:** устройства, диагностика и продление подписки,
   полный разбор платежа со сверкой, заметки и обращения, индивидуальные
   уведомления, единые права и аудит. Нужные API делать вместе с экранами.
3. **Операционная работа:** возвраты, очередь проблем и повторы обработки,
   управление сотрудниками, доработка тарифов, промокодов и рассылок в общей
   системе интерфейса. Затем оценить сохранённые представления, массовые
   действия с предварительным просмотром и дополнительные отчёты по фактической нагрузке.

### Критерии готовности

- [ ] Оператор находит клиента и открывает нужный раздел без поиска по длинному
  модальному окну; прямые ссылки, перезагрузка и возврат к списку работают.
- [ ] Из админки можно разобрать «оплатил, но подписка не появилась», «не могу
  подключить устройство», «нужно компенсировать простой», «не могу войти»
  и «не получил уведомление»: видны причина, доступное действие и его результат.
- [ ] Обращение можно назначить, снабдить внутренней заметкой и закрыть
  с историей решения; другой оператор видит выполненные действия.
- [ ] Для базовых сценариев выше не нужны ручные правки БД или обязательный
  переход в Remnawave/Supabase; внешние сбои и ограничения явно показаны.
- [ ] Повторный клик или повтор запроса не удваивает списание, начисление,
  возврат или продление; запрещённые действия блокируются также на backend.
- [ ] Существующие функции админки сохранены и проверены; добавлены проверки
  прав, финансовых правил, сбоев интеграций и e2e основных сценариев поддержки.
- [ ] Проведена визуальная проверка таблиц, карточек, форм и ошибок на desktop
  и небольшом экране, в том числе при длинных значениях и больших историях.

## 6. Общая ссылка и прямой переход к СБП для одного платежа ЮKassa

**Статус:** запланировано; требуется проверить ограничения текущего redirect-сценария.
**Добавлено:** 25 октября 2026 года.

### Проблема и желаемый результат

Сейчас создаётся платёж с общей ссылкой на страницу выбора способов оплаты
ЮKassa. На скриншотах владельца СБП скрыт за кнопкой «Ещё способы», поэтому
для перехода к нему нужны дополнительные действия.

Нужны две ссылки/кнопки для **одного и того же платежа ЮKassa**:

- «Оплатить» — общая страница с выбором способов оплаты.
- «Оплатить через СБП» — сразу СБП, без поиска в «Ещё способы».

Обязательное условие: один `payment.id` ЮKassa, одна сумма и один результат
оплаты. Один внутренний заказ с двумя разными платежами провайдера этому
требованию не соответствует. Второй переход не должен создавать новый платёж.

### Что удалось проверить

- Текущий backend в `apps/api/app/services/payments.py` использует
  `confirmation.type=redirect` и получает `confirmation_url`.
- В [документации «Умного платежа»](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/smart-payment)
  описана общая ссылка, а в [сценарии СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp)
  — создание платежа с `payment_method_data.type=sbp`. Это не подтверждает
  возможность получить две разные ссылки для одного уже созданного redirect-платежа.
  Документированного параметра для переноса СБП в первые плитки общей страницы
  в проверенных материалах не найдено; возможность настройки магазина нужно
  уточнить у ЮKassa.
- У виджета есть документированная возможность показывать несколько форм
  для одного платежа с общим `confirmation_token`, в том числе только СБП
  через `customization.payment_methods=['sbp']`. Доступность настройки нужно
  уточнить у менеджера. Источник:
  [настройка способов оплаты виджета](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/widget/additional-settings/separate-payment-methods).
  Это другой сценарий интеграции; совместимость с сохранением текущей внешней
  общей ссылки для того же `payment.id` пока не подтверждена.

### План разработки

- [ ] Уточнить у ЮKassa две возможности для текущего магазина: можно ли
  поднять СБП на первый экран общей страницы и можно ли официально получить
  прямую ссылку на СБП для того же `payment.id`, сохранив общую ссылку.
- [ ] Проверить подтверждённый способ в тестовом магазине. Не конструировать
  ссылку заменой пути `confirmation_url` или добавлением недокументированных
  параметров; наличие похожего URL в примере API не доказывает его применимость.
- [ ] Если две внешние ссылки для одного redirect-платежа не поддерживаются,
  подготовить вариант собственной страницы с двумя режимами виджета для
  одного embedded-платежа: все способы и сразу СБП. Ссылки на нашу страницу
  должны менять только режим отображения, сохраняя один платёж провайдера.
  Отдельно зафиксировать, что это меняет текущий способ открытия общей оплаты.
- [ ] До реализации выбрать подтверждённую схему. Если точное сочетание
  «существующая внешняя общая ссылка + отдельная ссылка СБП» недоступно,
  отметить ограничение и согласовать изменение сценария; не подменять
  требование созданием двух платежей.
- [ ] Добавить две кнопки там, где пользователь получает ссылку на оплату;
  привязать обе к существующему платёжному состоянию. При открытии и возврате
  проверять статус, срок действия и принадлежность платежа пользователю.
- [ ] Обеспечить единое завершение: после успеха любая из ссылок показывает
  результат, а пополнение или покупка применяется один раз по подтверждённому
  статусу провайдера. Проверить повторные клики, две вкладки и дубли webhook.

### Критерии готовности

- [ ] Общий выбор и переход сразу к СБП доступны без создания второго
  платежа ЮKassa; это подтверждено одним `payment.id` в API и обработке событий.
- [ ] СБП открывается без «Ещё способы»: на desktop доступен QR-код,
  на мобильном устройстве — переход к выбору банка.
- [ ] Сумма, назначение, клиент и результат совпадают для обеих ссылок;
  оплаченный или просроченный платёж не запускается повторно.
- [ ] Переключение способа, перезагрузка и параллельное открытие ссылок
  не создают повторного начисления или выдачи подписки.
- [ ] Работоспособность проверена в браузере и в текущих сценариях открытия
  оплаты из Telegram; использованы поддерживаемые ЮKassa механизмы.

## 7. Исправить выдачу trial и платных подписок для аккаунтов без email

**Статус:** локальное исправление подготовлено в `fix/auth-recovery-email`;
тестовые сценарии добавлены, общий прогон отложен до следующих дополнений.
**Приоритет:** высокий — VK-вход работает, но активация подписки без email заблокирована.
**Добавлено:** 26 октября 2026 года.

Реализованы нормализация и сохранение email, пропуск пустого поля в SDK,
обработка ошибок обоих DTO. Описание и оставшиеся проверки:
[подписки без email](auth-recovery-email.md). Статус production этим не меняется.

### Подтверждённая проблема

По диагностике владельца на сервере с версией `1.1.0`, коммит `ee62ec4`,
`POST /api/v1/subscriptions/trial` возвращает HTTP 500. Пример request ID:
`2732a44919634a6a8341bab19f1ec1f6`.

```text
ValidationError: CreateUserRequestDto
email
value is not a valid email address
input_value=''
```

У VK-аккаунта может не быть email. В `apps/api/app/integrations/remnawave/client.py`,
метод `provision_user`, вызов `CreateUserRequestDto(**create_payload)`
около строки 481 передаёт пустую строку в SDK. Валидация падает ещё до отправки
запроса создания пользователя в Remnawave. Аналогичное построение payload/DTO
есть в `upsert_user`; обработчики этих методов не перехватывают
`pydantic.ValidationError` при создании DTO.

В установленном SDK поля email обоих DTO объявлены как
`Optional[EmailStr] = None`. При реализации нужно подтвердить поведение
создания DTO и сериализации: отсутствие адреса нельзя передавать как `""`.
В `services/accounts.py` email из Supabase сейчас сохраняется без удаления
окружающих пробелов; строка из пробелов также может попасть в профиль/identity.

### План исправления

- [ ] Нормализовать `None`, `""` и строку из пробелов в отсутствие email.
  Непустой адрес обрезать по краям; некорректный непустой адрес не превращать
  молча в отсутствующий. Не генерировать фиктивные адреса и не делать почту
  обязательной для VK.
- [ ] Применить нормализацию в `provision_user` и `upsert_user` до поиска
  существующего пользователя и построения payload. При создании не передавать
  пустой email: использовать допустимый SDK вариант с пропуском поля или `None`.
- [ ] При обновлении без нового email сохранять уже существующий адрес
  Remnawave: отсутствие нового значения не должно очищать email пользователя.
  Проверить поведение `UpdateUserRequestDto` и сериализацию необязательных полей.
- [ ] Нормализовать email также при сохранении Supabase-пользователя в
  `apps/api/app/services/accounts.py`: создание и обновление `Account`,
  `AuthAccount` и поиск по подтверждённому email должны использовать согласованное
  значение. Пустое значение не должно затирать существующий адрес аккаунта.
- [ ] Перехватывать `pydantic.ValidationError` при построении обоих DTO
  в обоих методах и преобразовывать её в контролируемую ошибку интеграции
  с понятным API-ответом. Не оставлять необработанный HTTP 500 и не выводить
  полный payload/персональные данные в диагностику.
- [ ] Проверить транзакции выдачи trial: неуспешная валидация/выдача не должна
  расходовать право на пробный период или оставлять ложный статус активации.
  Повтор после исправления должен выдавать trial один раз.
- [ ] Проверить платную выдачу и повторы: отсутствие email не должно приводить
  к потере оплаченного права или повторному списанию/выдаче.
- [ ] Настройки VK и Supabase для этого исправления не менять. Перед любыми
  изменениями уже сохранённых данных отдельно определить необходимость
  нормализации старых пустых значений; массовое изменение не входит в саму диагностику.

### Обязательные проверки и критерии готовности

- [ ] Trial создаётся для аккаунта без email; варианты `None`, `""` и пробелы
  покрыты тестами. Ошибки валидации до отправки запроса не дают HTTP 500.
- [ ] Платная подписка создаётся без email, включая повторную обработку
  оплаченной операции без двойного списания или потери права на выдачу.
- [ ] Обновление без нового email сохраняет адрес в Remnawave и локальном
  аккаунте; корректный новый адрес передаётся без окружающих пробелов.
- [ ] После ошибки выдачи право на trial сохраняется; повторная успешная
  попытка активирует его один раз, дальнейший повтор не даёт второй trial.
- [ ] Ошибки обоих DTO в `provision_user` и `upsert_user` обработаны;
  обычные аккаунты с email и существующие Telegram-привязки продолжают работать.

## 8. Рассмотреть вход через Яндекс ID без повторного подтверждения email

**Статус:** правило доверия выбрано и реализовано локально; общий прогон,
настоящий вход и переход существующих пользователей ещё не проверены.
**Добавлено:** 26 октября 2026 года.

Текущее решение и его ограничения: [доверие email Яндекса](auth-recovery-email.md).
Повторное письмо исключается для адреса, совпадающего с почтовым логином
Яндекса в одном из пяти разрешённых доменов; прочие адреса требуют проверки.

### Проблема и желаемое поведение

При регистрации или входе через Яндекс пользователь получает дополнительное
требование подтвердить почту. Ожидание владельца: успешного входа в Яндекс ID
должно быть достаточно, чтобы продолжить вход в кабинет без отдельного письма.

До локального исправления адаптер `apps/api/app/api/v1/endpoints/yandex.py` возвращал
`email_verified=false`. Это объясняет возможное требование подтверждения
со стороны Supabase; точный результат зависит от настроек Auth и состояния
пользователя. Успешную аутентификацию провайдера и подтверждение владения
конкретным email нужно рассмотреть отдельно при выборе нового правила.

### План исследования и доработки

- [ ] Воспроизвести первый и повторный вход, зафиксировать причину запроса
  письма в Supabase и влияние существующего неподтверждённого пользователя.
  Проверить актуальное поведение используемой версии Auth.
- [ ] По официальной документации Яндекс ID проверить гарантии `default_email`,
  доступные признаки подтверждения и различия между адресом Яндекса, алиасами
  и возможными внешними адресами. Описать, каким данным можно доверять после
  проверки токена для нашего приложения и стабильного ID пользователя.
- [ ] Рассмотреть правило доверенного email только для `custom:yandex`,
  позволяющее обойти повторное письмо при достаточных гарантиях провайдера.
  Если явного признака подтверждения нет, отдельно описать основания и риски
  такого доверия, а также вариант входа по identity без доверия адресу для
  объединения аккаунтов. Не выдавать отсутствие признака за подтверждение.
- [ ] Проверить побочный эффект `email_verified=true` в Supabase:
  автоматическую привязку/объединение с уже существующим аккаунтом с тем же
  адресом. Решение не должно позволять получить чужой аккаунт только из-за
  совпадения email.
- [ ] Не отключать глобально подтверждение почты для email/password и других
  провайдеров. После выбора варианта реализовать изменение в минимальном
  объёме, обновить инструкции Яндекс ID и frontend-контракт.
- [ ] Проверить переход для уже созданных неподтверждённых пользователей:
  повторный вход не должен застревать в ожидании письма, создавать дубликат
  или терять баланс, подписку и Telegram-привязку.

### Критерии готовности

- [ ] Для согласованного доверенного сценария первый и повторный вход через
  Яндекс проходят без дополнительного письма Supabase.
- [ ] Отсутствующий/неподходящий email и конфликт существующего аккаунта
  обработаны явно; посторонний аккаунт не присоединяется по недоказанному адресу.
- [ ] Проверены существующие неподтверждённые пользователи, Google,
  email/password, VK без email и recovery; глобальные требования подтверждения
  почты для них не ослаблены этим изменением.
- [ ] Добавлены автоматические тесты выбранного правила и выполнен настоящий
  вход на тестовом окружении. Production меняется только по отдельной команде.
