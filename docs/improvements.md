## 3. Проверить сброс пароля с настоящим письмом Supabase

Код исправлен: recovery имеет приоритет, обработаны PKCE, reload,
недействительная ссылка, ошибка сохранения, отмена и поздний bootstrap.
Автоматические сценарии пройдены. Описание: [browser auth](auth-recovery-email.md).

Остались проверки на отдельной тестовой установке:

- [ ] Сверить шаблон письма и redirect allowlist: итоговый URL должен сохранять
  намерение сброса, а PKCE verifier — быть доступен в поддерживаемом браузере.
- [ ] Пройти «реальное письмо → форма → сохранение → вход новым паролем»;
  проверить отказ старого пароля, просроченную/повторную ссылку и отмену.
- [ ] Проверить переход из письма на другом устройстве/в другом браузере:
  при отсутствии verifier должен быть понятный запрос нового письма.

## 4. Завершить проверку настоящих входов Яндекс ID и VK ID

Интеграции входят в 1.1.0; дополнительные исправления подготовлены к 1.2.0.
Подписки без email (бывший №7) исправлены и покрыты регрессией. Правило
доверия почтовому логину Яндекса (бывший №8) реализовано; повторное письмо
может оставаться для прочих контактов. Сохранённые способы входа отображаются
в настройках клиента и карточке админки. Описание:
[browser auth](auth-recovery-email.md), [Яндекс ID](yandex-id.md), [VK ID](vk-id.md).

Автоматические проверки используют подменённые ответы провайдеров. Остаётся:

- [ ] На отдельной тестовой установке пройти настоящий первый/повторный вход
  Яндекса и VK, в том числе VK без email → trial → платная подписка.
- [ ] Проверить ранее неподтверждённого пользователя Яндекса, конфликт email
  и занятую identity; сохранить исходные баланс, подписку и Telegram-привязку
  без дубликатов. Автоматическая проверка адаптера не подтверждает поведение
  конкретной установленной версии Supabase Auth.
- [ ] Проверить реальные отказ/истечение кода/сбой провайдера, обновление
  и выход, referral intent, мобильный браузер и возврат из внешнего браузера.
- [ ] Подтвердить работу Google/email/password/recovery и отсутствие токенов,
  кодов и полных callback URL в журналах API/Auth/proxy тестовой установки.

Работающие сервисы и настройки production меняются только по отдельной
команде владельца. После ручной проверки закрыть этот пункт вместе с №3.


## 5. Полностью переработать админку для сопровождения клиентов

**Статус:** запланировано; требуется переработка интерфейса и расширение admin API.
**Добавлено:** 25 октября 2026 года.

### Цель

Сделать админку понятным рабочим инструментом: быстро найти клиента, понять
причину проблемы, выполнить доступное действие и увидеть результат и историю.
Пересмотреть структуру экранов, навигацию, визуальную иерархию и повседневные
сценарии поддержки. В объём входят необходимые изменения backend, схем БД,
интеграций и фоновых задач, если без них сценарий нельзя завершить из интерфейса.

### Основные проблемы

Логика и разметка сосредоточены в большом `App.tsx`; карточка клиента перегружена,
разделы не имеют самостоятельных адресов. Нужна понятная визуальная иерархия,
плотная компоновка и единые сценарии сопровождения. Не хватает полноценного
реестра платежей, admin API устройств, заметок, обращений и общей модели прав.
Существующие действия нужно сохранить при переработке.

### Новая структура интерфейса

- [ ] Сделать постоянную боковую навигацию по рабочим разделам: «Обзор»,
  «Клиенты», «Обращения», «Платежи и выводы», «Тарифы», «Промокоды»,
  «Рассылки», «События и диагностика», «Администраторы и доступ».
  В шапке разместить глобальный поиск и задачи, требующие внимания.
- [ ] Ввести адреса разделов и отдельных сущностей, breadcrumbs и прямые
  ссылки на клиента, платёж и обращение. Назад/вперёд и перезагрузка должны
  сохранять контекст, фильтры и страницу списка.
- [ ] Перенести подробную карточку клиента на отдельную страницу с краткой
  сводкой и вкладками: обзор, подписка и устройства, финансы, авторизация
  и привязки, обращения и заметки, события. Быстрый просмотр оставить компактным.
- [ ] Собрать единые таблицы, фильтры, статусы, формы и подтверждения действий.
  Настроить типографику, отступы, контраст, плотность данных и читаемые суммы
  и даты с явным часовым поясом; статусы различать текстом и цветом.
- [ ] Убрать декоративный шум, продумать пустые состояния, загрузку, ошибки
  и повтор запроса. Формы открывать по действию, показывать результат рядом
  с изменёнными данными. Проверить клавиатуру, фокус и небольшие экраны.
- [ ] Декомпозировать `App.tsx` на страницы, общие компоненты и слой работы
  с API; загружать историю и тяжёлые разделы по мере открытия.

### Функции, необходимые поддержке

| Направление | Что добавить или доработать | Зависимости backend |
| --- | --- | --- |
| Поиск клиента | Сохранить поиск по ID, email, Telegram ID и username; добавить переход к владельцу по ID платежа и Remnawave UUID. Быстрые ссылки между связанными сущностями. | Поиск по связанным данным, проверка прав, пагинация. |
| Карточка клиента | Сводка доступности услуги, срок подписки, баланс, устройства, последняя активность и проблемы, требующие внимания. Единая хронология с переходами к платежам и обращениям. | Агрегированная сводка; источники и время актуальности данных. |
| Подписка и Remnawave | Сверка локального состояния с панелью, обновление по запросу, выдача тарифа, продление на заданное число дней и компенсация за простой. Показать ошибку синхронизации и её результат после повтора. | Admin-команды поверх сервисов подписок, журнал изменений, согласованное обновление Remnawave и БД. |
| Устройства/HWID | Список устройств, базовый и оплаченный лимиты, удаление выбранного устройства и сброс привязок; изменение лимита с понятным учётом оплаченных устройств. | Admin API устройств поверх действующего сервиса; правила синхронизации описаны в [hwid-limit-sync.md](hwid-limit-sync.md). |
| Платежи | Полная история с фильтрами, ID провайдера, привязка к начислению или покупке, причина сбоя и события webhook. Действие «Проверить у провайдера» для зависшего платежа. | Реестр и детали платежей, серверная сверка, повтор обработки с защитой от двойного начисления. |
| Возвраты и компенсации | Различать реальный возврат через платёжного провайдера и корректировку внутреннего баланса. Показывать доступность, сумму, причину и итог операции. | Отдельный процесс возврата для поддерживаемых провайдеров, учёт ledger и влияния на подписку; ограничения неподдерживаемых способов. |
| Обращения и заметки | Небольшая очередь обращений: клиент, тема, ответственный, приоритет, статусы «новое / в работе / ждём клиента / решено», внутренняя заметка и история решения. | Хранение обращений, назначений и заметок с автором и датой, поиск и фильтры. |
| Связь с клиентом | Отправка индивидуального уведомления из карточки через доступный канал, шаблоны ответа, история и результат доставки. Показывать недоступность канала, например блокировку бота. | Адресная отправка через существующие сервисы уведомлений и Telegram, статусы доставки и контроль повторов. |
| Вход и привязки | Показать способы входа, историю привязок и конфликты identities; дать отправить письмо сброса пароля, когда этот сценарий исправлен. Для исправления привязки предусмотреть отдельный подтверждённый процесс. | Интеграция с auth и linking-сервисами; не показывать пароли и токены, не допускать потери последнего способа входа. |
| Очередь проблем | Выводы в ожидании, зависшие платежи, ошибки выдачи подписки/синхронизации и недоставленные сообщения с переходом к клиенту и доступному действию. | Выборки проблемных состояний, фоновые проверки, время последней попытки и результат. |
| Права и аудит | Права поддержки, финансового оператора и владельца; управление доступом сотрудников. Просмотр кто, когда, что и почему изменил, с состояниями до/после. | Единые проверки прав на backend, административные endpoints и полный журнал действий. |

### Требования к backend и операциям

- [ ] Переиспользовать действующие сервисы ledger, платежей, подписок,
  устройств и уведомлений. Финансовые изменения проводить через ledger,
  а не прямой записью баланса или ручной установкой статуса «оплачен».
- [ ] Добавить admin endpoints для недостающих сценариев с правами на каждое
  действие, валидацией, понятными кодами ошибок и серверной пагинацией/фильтрами.
- [ ] Для денежных операций, выдачи/продления подписки, возвратов и повторов
  обработки предусмотреть идемпотентность и защиту от параллельных действий.
  Перед изменением показывать клиента, последствия и итоговые значения;
  сохранять причину, оператора и результат в аудите.
- [ ] Для операций с внешней системой отображать состояния «выполняется /
  успешно / ошибка» и проверяемый итог. Предусмотреть восстановление после
  частичного сбоя, чтобы интерфейс не сообщал успех раньше фактического результата.
- [ ] При ручном изменении подписки или устройств явно показывать, как оно
  влияет на оплаченный срок, дополнительные устройства и дальнейшее продление.
- [ ] Хранить обращения и заметки в БД, ограничивать их видимость правами;
  добавлять миграции и тесты новых правил вместе с реализацией.

### Порядок реализации

1. **Основа интерфейса:** карта сценариев поддержки, новая навигация, общие
   компоненты, реестр клиентов и полноценная страница клиента. Проверить
   компоновку на реальных объёмах данных и перенести существующие действия.
2. **Базовое сопровождение:** устройства, диагностика и продление подписки,
   полный разбор платежа со сверкой, заметки и обращения, индивидуальные
   уведомления, единые права и аудит. Нужные API делать вместе с экранами.
3. **Операционная работа:** возвраты, очередь проблем и повторы обработки,
   управление сотрудниками, доработка тарифов, промокодов и рассылок в общей
   системе интерфейса. Затем оценить сохранённые представления, массовые
   действия с предварительным просмотром и дополнительные отчёты по фактической нагрузке.

### Критерии готовности

- [ ] Оператор находит клиента и открывает нужный раздел без поиска по длинному
  модальному окну; прямые ссылки, перезагрузка и возврат к списку работают.
- [ ] Из админки можно разобрать «оплатил, но подписка не появилась», «не могу
  подключить устройство», «нужно компенсировать простой», «не могу войти»
  и «не получил уведомление»: видны причина, доступное действие и его результат.
- [ ] Обращение можно назначить, снабдить внутренней заметкой и закрыть
  с историей решения; другой оператор видит выполненные действия.
- [ ] Для базовых сценариев выше не нужны ручные правки БД или обязательный
  переход в Remnawave/Supabase; внешние сбои и ограничения явно показаны.
- [ ] Повторный клик или повтор запроса не удваивает списание, начисление,
  возврат или продление; запрещённые действия блокируются также на backend.
- [ ] Существующие функции админки сохранены и проверены; добавлены проверки
  прав, финансовых правил, сбоев интеграций и e2e основных сценариев поддержки.
- [ ] Проведена визуальная проверка таблиц, карточек, форм и ошибок на desktop
  и небольшом экране, в том числе при длинных значениях и больших историях.

## 6. Согласовать и проверить включение отдельной оплаты СБП

Подготовлена альтернатива с embedded-виджетом ЮKassa: одна общая ссылка
и одна ссылка в режиме СБП на один `payment.id`. Код и автоматические проверки
готовы; `YOOKASSA_WIDGET_ENABLED=false` по умолчанию. При включении общая ссылка
для новых платежей тоже ведёт на нашу страницу. Поддержка точного сочетания
«старая внешняя общая ссылка + внешняя СБП-ссылка» не подтверждена.
Описание, источники и настройка: [СБП и общая оплата](sbp-checkout.md).

В hotfix 1.2.1 исправлен доступ к checkout по платёжному ticket без сессии
кабинета. Выбор оформлен двумя карточками «Картой и другими способами» и «СБП»
на странице оплаты и у незавершённых widget-платежей. Обе используют один
платёж; переход к СБП не создаёт повторную оплату. Проверка реального магазина
остаётся необходимой.

Остаются внешние условия включения:

- [ ] Подтвердить у ЮKassa возможности конкретного магазина: доступность
  `customization.payment_methods=['sbp']`, а также настройку порядка плиток
  и прямой ссылки в прежнем redirect-сценарии, если он предпочтительнее.
- [ ] Владелец принимает замену общей страницы оплаты вариантом с виджетом
  либо сохраняет текущий redirect до ответа ЮKassa. Подготовленный вариант
  выключен по умолчанию; сам PR/выпуск не меняет уже установленное значение
  `YOOKASSA_WIDGET_ENABLED`.
- [ ] Проверить платёж в разрешённом тестовом сценарии магазина: один ID
  в обеих ссылках, QR на desktop, выбор банка на телефоне, возврат из банка
  и Telegram. Подменённый скрипт в e2e не подтверждает доступность СБП.
- [ ] Проверить HTTPS, маршрут `/checkout`, CSP при наличии внешнего proxy,
  ограничения storage/всплывающих окон и завершение webhook/сверки без
  повторного начисления. Затем дать отдельную команду на деплой/включение.
