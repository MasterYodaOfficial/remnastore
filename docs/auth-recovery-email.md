## Подписки без email

Причина инцидента в 1.1.0: VK-аккаунт без email передавал `email=""`
в `CreateUserRequestDto`, валидация SDK завершалась необработанной ошибкой.
Пример request ID: `2732a44919634a6a8341bab19f1ec1f6`.

- `None`, пустая строка и пробелы приводятся к отсутствующему адресу;
  корректный адрес очищается от окружающих пробелов.
- При создании и обновлении Remnawave поле отсутствующего email опускается
  в обоих путях: `provision_user` и `upsert_user`. Установленный SDK допускает
  `None` и сериализует запросы с `exclude_none=True`, поэтому старый адрес
  Remnawave не очищается. Поиск по пустому адресу не отправляется.
- Та же нормализация применяется при сохранении Supabase-пользователя
  в `Account` и `AuthAccount`, а также при поиске по подтверждённому email.
  Пустое входящее значение сохраняет имеющийся локальный адрес.
- `ValidationError` обоих DTO преобразуется в `RemnawaveRequestError`
  с нейтральным сообщением, без включения некорректных полей в ошибку.
  Существующие обработчики подписок возвращают контролируемую ошибку интеграции.
- Фиктивные адреса не создаются, email для VK не становится обязательным.
  Массовая правка данных и конфигурация провайдеров не требуются.

Подготовлены проверки реальных DTO SDK, сохранения существующего адреса,
Supabase upsert, trial без email, повторного trial после ошибки валидации
и покупки из кошелька без email с повтором того же idempotency key.
Webhook-выдачу и повторы оплаты также включить в общий регрессионный прогон.

## Доверие email Яндекса

`/info` не содержит признака `email_verified`. Поэтому введено узкое правило
для `custom:yandex`: после проверки токена для нашего `client_id` и стабильного
ID адрес проходит `EmailStr`, его локальная часть должна совпадать с `login`
из серверного ответа Яндекса, а домен входить в список `yandex.ru`, `ya.ru`,
`yandex.com`, `yandex.by`, `yandex.kz`. Сравнение без учёта регистра.
Только тогда адаптер возвращает `email_verified=true`.

Это правило проекта на основании принадлежности почтового логина, а не
полученный от Яндекса claim о подтверждении. Одного домена недостаточно.
Произвольные контакты, внешние адреса, домены 360 и несовпадающие алиасы остаются
`email_verified=false`; для них Supabase может запросить письмо. Некорректный
адрес даёт 422. Глобальное автоподтверждение Supabase не включается.

Основания: [поля профиля Яндекс ID](https://yandex.ru/dev/id/doc/ru/user-information),
[логины и адреса Яндекса](https://yandex.ru/support/id/ru/authorization/email),
[дополнительные почтовые адреса](https://yandex.ru/support/yandex-360/customers/mail/ru/web/preferences/about-sender/additional-addresses).

Подготовлены тесты доверенных доменов, несовпадающего логина, отсутствующего
логина, внешнего и некорректного адреса. Реальный первый/повторный вход,
поведение существующего неподтверждённого пользователя и конфликты аккаунтов
нужно проверить на тестовой установке Auth. Поскольку подтверждённый email
может участвовать в объединении аккаунтов, проверить сохранение баланса,
подписки и Telegram-привязки обязательно. Никакие identities не перепривязываются
скриптом и не удаляются этим изменением.

## Сброс пароля Supabase

Recovery определяется до обычного bootstrap и имеет приоритет при отрисовке.
В установленном SDK PKCE-переход может уведомлять `SIGNED_IN`, а не
`PASSWORD_RECOVERY`: SDK теряет тип перехода в PKCE-ветке. До инициализации
сохраняется признак `/PASSWORD_RECOVERY` из PKCE verifier; успешный обмен
помечает именно полученную сессию. Обрабатывается и `PASSWORD_RECOVERY`.
Сам `auth_action=reset-password` задаёт экран, но не подтверждает сессию.

Маркер в `sessionStorage` связан с ID пользователя и `session_id`, переживает
перезагрузку той же вкладки и обновление токена. Дополнительная копия токена
не сохраняется. При инициализации recovery и перед сохранением вызывается серверный `getUser`.
Старая обычная сессия не принимается вместо неудачного восстановления.
Поздние результаты bootstrap блокируются счётчиком поколения auth-состояния.
В обработчиках событий SDK нет ожидающих вызовов его Auth API.

Просроченная ссылка, ошибка обмена и отсутствие verifier показывают запрос
нового письма. Ошибка сохранения сохраняет форму; ошибка недействительной
сессии переводит на экран истёкшей ссылки. После успеха очищаются параметры
URL и recovery-маркер, затем загружается кабинет. Отмена очищает маркеры
и завершает локальную сессию; во время сохранения отмена недоступна.

Подготовлены unit/component и браузерные сценарии с подменёнными ответами:
PKCE, reload, старая сессия, истёкший код, отсутствие verifier, ошибка/повтор
сохранения, отмена и гонка bootstrap с `PASSWORD_RECOVERY`.
Они не заменяют реальное письмо. Для PKCE письмо нужно открывать в контексте,
где доступен verifier; открытие в другом браузере/устройстве не становится
поддерживаемым только благодаря наличию URL-маркера.
